# Mango v13c development snapshot audit

This is an audit of an in-progress file, not the final v13c result. I copied the report to `snapshots/v13c-development-capabilities.json` before analysis. The frozen copy has SHA-256 `f6d8ae59549a7198051d51e59e04bfcc20a973da23f3b05a062eff179a19fe8e`, status `partial`, and 82 activities. The live file advanced during the initial read (80 → 82 activities and its transient new host changed), demonstrating why its missing-host set must not be treated as a regression or final ownership result.

The frozen snapshot newly emits 69 facts for `com.mgtv.ui.skin.SkinDetailActivity`: 36 settings, 18 operations, 9 bridge removals, and 6 callbacks. This is a false host binding. `SkinDetailActivity.obtainLayoutResourceId()` returns `R.layout.activity_skin_detail`; that XML contains title, recycler, radio, text, and container views but no WebView. Its own initialization only resolves those non-WebView IDs (`SkinDetailActivity.java:488-496`).

Every one of the 69 WebView facts instead comes from Tencent sharing paths. Their receiver evidence is `com.tencent.open.b.b`, with routes through `QQShare.shareToQQ`, `QzoneShare.shareToQzone`, or `Tencent.shareToQQ/shareToQzone`, eventually reaching `TDialog.a()/b()`. The Activity can initiate sharing, but no source evidence binds the SDK dialog's internal WebView to the Activity layout or lifecycle as an owned WebView. XML discovery appears to have propagated from an ordinary Activity/root layout into reachable helper calls and then seeded all methods of a remotely constructed SDK WebView/dialog.

This confirms the reported generic failure mode: resolving a layout or a reachable helper is insufficient to seed every method on a discovered WebView class. A valid rule needs a concrete XML WebView node or `findViewById` result tied to that node, followed by actual constructor/lifecycle calls and field aliases. Calls that create a separate dialog or share UI require their own construction/attachment edge and must retain separate ownership.

The v12j baseline remains 92 hosts. No final v13c host delta or ownership judgment is made from this snapshot. The final audit must restart from the completed report and retain this false-positive case even if a later candidate removes it.

## Correction after final report

The earlier `false host ownership` verdict was too strong and is withdrawn. The observation came from transient phase-0/current-host expansion; `SkinDetailActivity` is absent from both final v12j and final v13c. Source also proves a real conditional call chain that the initial note had not checked: title-bar callback `b.onClick`, branch `b12 == 2`, calls `showShareDialog()`; when `Q != null`, that method calls `MGShare.goShare(this, shareInfo, ...)`. Thus the Activity instance is passed as the share Context and a Tencent share dialog may be conditionally constructed. The 69 transient facts still do not prove that every QQ/Qzone branch executes, but they cannot be rejected merely because the Activity XML has no WebView. Their correct status is **transient conditional candidate, final-output absent**, with channel/branch and dialog-construction ownership requiring separation.
