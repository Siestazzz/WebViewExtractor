# v16 callback entry repair

For mgadplus, the missing entry is an already registered message handler, not construction of an arbitrary callback. `am.a.z(k)` stores `new am.a$q0(k)` under the literal route `showMedia` through `BridgeWebView.t(String,a)`. Registry dispatch invokes the exact stored `q0.handler(String,d)`. That callback writes its outer `am.a.f2663h` and calls `Y(data,k)`. The H5 branch in `Y` calls `Q()` and then `I`; `Q` installs the fifteen lost handlers, while `I -> D` calls `U`, which installs the exact `am.a$w` lifecycle listener. A generic repair needs map-instance/key/value identity and the captured `q0.this$0`/`k` aliases.

For DTF, the path starts from a real Activity lifecycle entry. `FaceLoadingActivity.onResume` calls `I()` once. `I` constructs the exact `FaceLoadingActivity$h`, passes it through `baseverify.d.a`, and registers the returned callback adapter at `y5.b.e(Map,APICallback)`. Successful dispatch reaches the exact three-String `h.onSuccess`, which validates the protocol and calls `C` or `z`; the NavigatePage branch of `z` calls `J`. `J` constructs `ToygerWebView` into the same Activity's field `M`, and its constructor synchronously calls `init`. Error members do not reach this construction and must not be expanded into it.

For Pangle, source does not show a required asynchronous callback immediately before the lost registration. The common bridge builder `j(WebView)` owns the concrete WebView and defaults its name field to `IESJSBridge`; `r.c(j)` synchronously copies both and installs the interface. The audited `adexpress.bp.bp.c(WebView,r,String)` overload is also synchronous: it creates or reuses the exact `adexpress.bp.z` and immediately calls `addJavascriptInterface`. The generic repair should follow these builder/factory calls only when their WebView instance is host-reached. Adding a synthetic callback edge before `bp.c` would recreate the construction-seeding bug.
