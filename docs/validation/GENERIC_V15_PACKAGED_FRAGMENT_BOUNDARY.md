# Generic v15: packaged Fragment SDK bodies are framework contracts

v14 introduced actual Fragment transaction installation but used the older frameworkViewAccess guard. That guard accepted Android implementations and the AndroidX Fragment class, while rejecting body-bearing AndroidX FragmentActivity, FragmentManager and FragmentTransaction declarations as if they were application overrides. Synthetic fixtures lacking packaged SDK bodies did not exercise the rejection.

The v14 Txws frozen report finishes WebviewBaseActivity in approximately 0.44 seconds with no pending contexts, but records FragmentManager/BackStackRecord constructor expansion and a non-installed WebViewBaseFragment. This is not evidence of deadline exhaustion. Independent source and packaged DEX evidence confirms the actual showFragment chain uses the public AndroidX getSupportFragmentManager, beginTransaction, replace(int,Fragment,String), and commit contracts. The six affected hosts lose the same shared setting/client surface.

A separate frameworkFragmentAccess guard now applies only to the explicitly modeled public Fragment acquisition/transaction signatures. Its actual declaring class must be one of Fragment, FragmentActivity, FragmentManager or FragmentTransaction in the native, AndroidX or support-v4 contract family. A packaged body for those exact SDK declarations does not disable their model. An actual application override remains outside this boundary; a null-returning override does not install a Fragment. No arbitrary AndroidX method or application namespace is accepted, and no constructed Fragment is independently activated.

PackagedFragmentProtocolProbe compares missing SDK bodies with implemented SDK declarations and includes application override, uncommitted transaction and allocated-only negatives. Frozen v14 produces three categories for the missing-body control and zero for the implemented-SDK positive, proving the previous fixture gap. Its source and frozen result are under test/runs/txws-v14-fragment-source. Current positive recovery and full-suite results will be recorded after final integrated validation.

This is a bounded SDK semantic model, not a complete Fragment runtime emulator. Actual custom manager/transaction implementations, their explicit-super forwarding, restored-state attachment, XML Fragment inflation and navigation controllers remain separate precision/coverage boundaries. The model retains actual transaction and Fragment identities and requires installation evidence.

The integrated negative initially exposed another necessary guard: beginTransaction must not produce a transaction from a null/unknown manager returned by an application override. Acquisition now requires actual compatible receiver values; unresolved/nullable unions retain the conservative generic path rather than inventing a manager. The application-null-override fixture passes after this correction. The public show(Fragment) fluent result preserves the same transaction identity and does not independently activate its argument; the installed add/replace operation and commit are still required.

Parent's isolated current-Engine overlay over frozen v14 restores the actual Txws WebviewBaseActivity's 13 settings and 22 callbacks. That is one-host diagnostic evidence only; v14's substantial multi-app losses are not all proven to share this cause. Full v15 ten-app validation remains required.

Final integrated validation: capabilitySelfTest, compactReportTest and shadowJar all passed in 20 seconds (`test/runs/generic-v15-freeze-tests.log`), including packaged SDK-body recovery, show fluent identity, application override-null, uncommitted and allocated-only negatives. This build also includes bounded Class identity refinement and the reflection discovery necessary-condition prefilter. Multi-APK acceptance is not inferred from these tests.
