Report-guided supplemental evidence; frozen gold is unchanged. The matching decompiled build and report use APK SHA-256 `c4a8d2904ec530a4b97d8dbd04cd641f175918f24cff5d056d216e3808852941`. Exact source file hashes, quoted line locations, current host coverage and report hash are in the companion JSON.

The nine YSP hosts have 171 missing raw rows: 99 settings, 18 Client callbacks, nine bridge registrations, nine Java `invoke` methods, and 36 message handlers. None has a YSP receiver/site in the current output. Only three of the nine Activities appear in output at all. This is a common object-entry loss candidate, not evidence that each bridge registration individually failed. The report ended with traversal limits; no causal claim about the engine is established merely from absent output.

The default service registration maps the class key `ysp.b` to `YspPlayerService`; its factory returns a concrete `YspMediaPlayer`. VideoPlayManager stores the product and calls attach with its actual Context and TNVideoView. GlobalLivePlayer uses the same factory and attaches its retained product to a nonnull actual ViewGroup. Attach allocates an anonymous BaseWebView subclass, retains it in a field, applies seven direct settings, and registers Client `b`. A new bridge `f` captures that same field in its final WebView field and registers itself as `YspJSBridge`. The same WebView field is then passed to the ViewGroup insertion helper. Conditions are YSP mode selection, the default non-QFix path, a nonnull owned container, and first attach when the WebView field is null.

A generic fixture should model a generated class-key service registry, interface factory result retained in a manager field, interface attach dispatch, and WebView identity passing into a bridge constructor. Probe each boundary independently before attributing the real omission to service resolution, reachability or relevance pruning. Source includes only seven attach settings directly; the other frozen YSP settings depend on inherited BaseWebView initialization and need their own source-chain check.

The four missing TencentVideoWebViewClient `onReceivedTitle` facts are legitimate custom forwarding. A registered WebChromeClient `k` holds the very CustomWebViewClient selected by the factory, then its standard title callback forwards the actual WebView and title to that held object. The Tencent-domain selection makes the virtual target TencentVideoWebViewClient. This method belongs to a custom Client class but is reached from the registered Chrome callback. A generic fix should preserve captured object identity and ordinary virtual dispatch; adding this signature to the standard WebViewClient contract would misrepresent the evidence.

This document is a development diagnosis, not acceptance or a complete audit of all nine host attachment chains. Existing independent host proofs are referenced through the frozen oracle; current source review independently verifies the shared service/product/registration implementation.

The service creator uses `Class.getDeclaredConstructors()[0]`, marks the selected Constructor accessible, and calls `Constructor.newInstance(new Object[0])`. Its Class comes from the generated APIMeta implementation field. The service is cached in APIMeta for singleton lookup. Constructor-array reflection is therefore a specific generic fixture boundary; supporting only Class.newInstance would not cover this chain. No engine trace has yet certified it as the actual failure.

The inherited settings receiver is also concrete: the anonymous WebView calls BaseWebView(Context), then private init calls allowMixedContent and setDefaultSetting. These obtain settings from the same this and configure mixed-content, remote-value DomStorage, file access and text zoom. YSP attach subsequently writes DomStorage=true and mixed-content=0 on that same instance, so the earlier dynamic DomStorage write must not be mistaken for the final setting value.
