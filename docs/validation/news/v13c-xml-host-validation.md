# v13c XML host validation

This review uses the fixed four-host development extract and compares it with v12j. It is not a full v13c ownership audit. All XML-derived rows are candidates, and candidate rows are counted as wrong when their object ownership lacks source support.

The four host identities are correct. Both privacy activities resolve `web_detail_webview` in `init_web_browser_layout` to `X5WrapperWebView`. WebNovel resolves the ordered nested layout chain to the inner `AdWebView`. Support now follows the real `BaseActivity.inflate(...,false) -> addView` path and resolves `activity_support/webView` to `BaseWebView`.

The larger row counts are not wholly new capabilities. In both privacy hosts, the eight settings and `setWebViewClient` already present in v12j are the same source sites with a changed receiver representation. Source applies them to `PrivacyAbsWebActivity.webView`, which is the XML object, while v13c reports an XML-backed unknown union. The six X5 SDK constructor removals execute on that object. DtX5 bridge injection is reachable when the object loads a URL. By contrast, seeded `loadData` and `loadDataWithBaseURL` overrides have no demonstrated host call, and WeakReference/compatibility/debug-constructor objects are not aliases of the XML view.

WebNovel’s twelve `NovelWebView.setWebViewSettings` calls target `NovelWebView.mWebView`, obtained from `NovelLoadingWebView.getWebView`; this is exactly the nested `AdWebView`. Those true settings remain an unknown union in the report. The new eleven `AdWebView.initWebViewSettings` rows are different: WebNovel never calls that method. They come from seeding the XML component class and are false expansion even though their receiver type is the correct class. The same rule excludes uncalled `loadData` variants and unbound compatibility alternatives.

Support’s direct settings, clients, and loads use field `SupportActivity.ˋˋ`, populated by `findViewById(webView)`, so they belong to the same BaseWebView. Constructor defaults and a load-triggered DtX5 bridge can also belong to that object through its inheritance chain. The separate twelve-row `DtX5WebView` identity under `com.tencent.news.utils.r.ˆ` is not another UI view. That helper constructs a DtX5WebView only when its WebView argument is null; Support passes the field after mandatory initialization. It is a nullable fallback/alias pollution path. `hardReset`, `softReset`, uncalled load variants, the incompatible `android.webkit.WebView` helper branch, and unresolved WeakReference/entry/constructor parameters likewise cannot be accepted as Support ownership.

The reusable implementation constraint is reachability, not only subtype compatibility. XML discovery should preserve one allocation identity through parent types and field/getter chains. It should schedule a superclass constructor, an invoked override, and real lifecycle callbacks, but it must not seed every relevant method declared on the discovered component. Nullable fallback allocations need their own identity and a feasible null branch. Object-typed compatibility helpers must retain only branches compatible with the concrete XML hierarchy.
