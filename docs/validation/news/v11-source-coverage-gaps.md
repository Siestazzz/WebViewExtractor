# News source coverage and acceptance gaps at v11

The legacy public development-v3 document claims 30 deeply checked hosts. It is useful historical evidence, but is not a current strict source-audit certificate. The current frozen oracle also contains exactly 30 Activity names, including two disputed owners: AdBonusPageActivity was explicitly left unproven by the v16e source review, and SplashAdDynamicPreviewActivity's emitted EasterEgg preload path uses an application Context and does not prove its own attached WebView. Both old expectations remain in frozen gold. Among those 30, at most 28 are currently reusable source-positive candidates; that number is not a certification that all 28 have complete capability surfaces.

There is no current source_audit.json in the strict contract format mapping each Activity's bridge/settings/callback coverage to done/partial/unknown, or identifying actual binding strata and their deeply checked host names. Source ownership validity alone cannot fill that gap. The older group inventory includes unowned components, one-host groups, callback class summaries and broad shared business handlers; these need concrete registration/member closure before being counted as deep.

The existing development group inventory already exposes likely stratum shortfalls: security/direct Activity, support/direct Activity and novel/direct Activity can share a source-defined direct-binding stratum, but SDK payment platform selection, ad native-provider, ad page-wrapper and shared EasterEgg-controller groups each have only one independently supported public representative in that inventory. The last group cannot count the two disputed sibling owners. These are candidate strata requiring an explicit justified taxonomy; no one-host SDK family is silently merged just to reach two. Fragment/factory YSP and inherited browser families have multiple source-positive candidates, but must retain their concrete host chains and complete three-category surfaces.

The v10 all-output host audit covers all 33 emitted Activities, including candidate bindings, with 32 valid and one unresolved. That is an ownership result, not a capability-precision result. Current source-confirmed wrong alternatives, ambiguous captures, unrelated shared dispatcher branches and callback/bridge receiver aliases need a separate report-bound bridge/settings/callback precision document. The synthetic wrong-registry-key case is a precision warning for engine behavior, not evidence that every real News host or capability is wrong.

Holdout status claims ten undisclosed verified Activities. Those identities/facts were not read for this review and remain untouched. The public status document alone does not prove the strict sealing timestamp/hash, nonoverlap with development hosts or current report-bound per-category evaluation. Merging holdouts into the development set to make 30 would violate the current nonoverlap requirement. Performance also requires three fresh independent runs of the same candidate jar, within the external 600-second limit; a single fast report is insufficient.

Next source work should close additional non-holdout owners already supported by concrete chains, document each primary registered bridge/settings/callback surface, settle or retain the two disputed bindings with separate versioned evidence, and build the explicit stratum/deep map. Frozen misses remain visible throughout. No exhaustive-below-30 proof exists: the source inventory retains unresolved fragments, factories, plugin/reflection edges and decompiler errors.
