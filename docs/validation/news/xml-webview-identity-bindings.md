# XML WebView identity bindings

These three mismatches have the same shape: Android inflates a concrete XML class, while Java/Kotlin immediately stores it in a parent-typed local or field. There is no later cast back to the concrete class. The concrete identity must therefore travel from the selected layout inflation, through `findViewById`, into the parent-typed field.

For privacy, `PrivacyAbsWebActivity.onCreate` selects `init_web_browser_layout` (`2131493563`, `0x7f0c02bb`). That layout's `web_detail_webview` (`2131303140`, `0x7f091ae4`) is an `X5WrapperWebView`. Source retrieves it as `View`, checks/casts only to `com.tencent.smtt.sdk.WebView`, and stores it in `webView` with that parent type. No source downcast to `X5WrapperWebView` exists. The runtime type remains the XML class through `X5WrapperWebView -> DtX5WebView -> smtt.WebView`.

For support, `SupportActivity.onCreate` selects `activity_support` (`2131493004`, `0x7f0c008c`). Its `webView` (`2131303125`, `0x7f091ad5`) is a `BaseWebView`. `m135947` casts the lookup result directly to `com.tencent.smtt.sdk.WebView` and stores it in `f109620`, also declared as the parent. The concrete chain is `BaseWebView -> RecyclableWebView -> X5WrapperWebView -> DtX5WebView -> smtt.WebView`; the XML tag is the only concrete-type source.

Novel has a three-layout composition. `WebNovelActivity.m125784` selects `web_novel_layout` (`2131495279`, `0x7f0c096f`), whose `web_advert_view` (`2131303127`, `0x7f091ad7`) is `NovelWebView`. That view inflates `web_advert_view_layout_novel` (`2131495274`, `0x7f0c096a`) and finds `loading_webview` (`2131299735`, `0x7f090d97`) as `NovelLoadingWebView`. The loading view inflates `ad_loading_web_view_novel` (`2131493047`, `0x7f0c00b7`); its `web_detail_webview` (`2131303140`, `0x7f091ae4`) is the actual `AdWebView`. The first lookup casts it to `BaseSysWebView`, and all subsequent fields/getters, including Activity field `f101623`, keep that parent type. `NovelWebView` and `NovelLoadingWebView` are containers; `AdWebView` is the API receiver.

The ID `web_detail_webview` is reused in unrelated layouts. A reusable implementation must first resolve the Activity's `setContentView` result, then follow only nested `inflate(layout,parent,true)` edges from that tree. Joining all occurrences of `0x7f091ae4` would cross-bind privacy, novel, and other WebViews.

## Inflation and lookup roots

`PrivacyAbsWebActivity.onCreate(Bundle)` passes the static resource constant `privacy.f.f91788` directly to the framework `Activity.setContentView(int)`. Its later unqualified `findViewById(res.g.De)` therefore searches that Activity content tree. The result is stored in the DEX field `PrivacyAbsWebActivity.ˊˊ:smtt.WebView`; the selected XML node supplies the more precise `X5WrapperWebView` identity.

`SupportActivity.onCreate(Bundle)` passes the static constant `p0.f90509` to the inherited `BaseActivity.setContentView(int)`. That override installs a base layout, finds its content `ViewGroup`, inflates the requested `activity_support` with `inflate(i, viewGroup, false)`, and explicitly calls `viewGroup.addView(returnedRoot)`. `SupportActivity.ˉˆ()V` (JADX `m135947`) then calls Activity `findViewById`, so its root is the now-attached Activity tree. It stores the node in DEX field `SupportActivity.ˋˋ:smtt.WebView`.

`WebNovelActivity.onCreate(Bundle)` obtains the layout through virtual method `WebNovelActivity.ˈᵢ()I` (JADX `m125784`). Its normal branch returns static constant `tad.g.f105386`; the PatchRedirector branch remains dynamic. The inherited `BaseActivity.setContentView(int)` uses the same `inflate(layout, contentParent, false)` followed by `addView` sequence. `initView()` searches from the Activity tree and obtains the outer `NovelWebView`.

The nested Novel layouts use different semantics. `NovelWebView.init(Context)` invokes `inflate(tad.g.f105384, this, true)`, so the inflated children attach to that exact `NovelWebView`; its unqualified `findViewById(loading_webview)` is rooted at `this`. XML construction normally enters the `(Context, AttributeSet)` constructor, while both public constructors call `init`. `NovelLoadingWebView` delegates its shorter constructors to `(Context, AttributeSet, int)`, which calls `initialize(Context)`. That method invokes `inflate(tad.g.f105201, this, true)`; the layout root is `<merge>`, so this parent and `attachToRoot=true` are required. Its lookup of `web_detail_webview` is rooted at that same `NovelLoadingWebView` after the merge children are attached.

A synthesis fixture should preserve four distinctions: direct framework `setContentView(constant)`; an inherited wrapper that performs `inflate(layout,parent,false)` then `addView`; a virtual layout provider with a constant normal return and an unknown patch branch; and custom-view constructors that perform `inflate(layout,this,true)` followed by `this.findViewById`. Resource IDs are joined only inside the resulting rooted layout tree.
