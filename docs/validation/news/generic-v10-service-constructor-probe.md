# Generic reflected service construction: frozen v10 probe

Run `test/run-service-constructor-probe.sh` from the repository. An optional first argument selects another jar; an optional second argument selects an isolated output directory. The runner compiles only `ServiceConstructorArrayProbe.java` against the selected jar and never recompiles production sources or loads build/classes. The default is the frozen `test/runs/generic-v10.jar`. Exact fixture, jar and result hashes are in the companion JSON.

The synthetic DEX uses generic `probe.*` names. It models a class-name outer Map and literal default-key inner Map, Meta.implClazz, optional creator with static default creator, declared-constructor-array reflection with setAccessible and an empty Object array, singleton cached object, service-interface factory, retained product-interface field, owned ViewGroup attachment, WebSettings setter, registered Client/member, and registered annotated Bridge/member. Instruction-building helpers follow the existing CapabilitySelfTest fixture conventions; this standalone file has no dependency on its current compiled version. Branch targets are calculated in DEX code units.

Twenty-four differential cases cover Map present/absent, cache present/absent and six creator variants. Direct construction controls produce one bridge, callback and setting each. Both Class.newInstance and Constructor-array variants produce zero in all configurations. A creator-local const-class variant also produces zero: no Meta field, Map or parameter propagation is needed to reproduce this failure.

The first isolated failure is ordinary reflective object construction feeding a return value. In the creator-local constant case, DexFlow preserves the exact `probe.Implementation` Class in the Class.newInstance call. Its return remains a generic `java.lang.Object` expression. The later Service.create and Product.attach interface invocations are unresolved; no WebView receiver reaches the report. This establishes an earlier boundary than constructor-array selection. It does not prove that fixing that boundary alone restores all real News host paths.

The actual constructor-array chain remains a separate required positive: getDeclaredConstructors, AGET_OBJECT index zero, setAccessible(true), new Object[0], Constructor.newInstance, service-interface factory and product-interface attach. The synthesized Implementation has exactly one packaged no-argument constructor, so array order cannot introduce ambiguity in this probe. The source-based real registration, selected class and invocation conditions remain in the preceding News YSP audit document.

The missing-default-key negative exposes a second issue. Even with the source-equivalent null-Meta guard, the direct creator produces all three capabilities for a missing registry key. Therefore its positive counterpart is not proof of precise Map semantics. The result JSON marks those two cases `wrong`; they must remain negative constraints during repair. The no-Map cases bearing the same variant name remain positive because they deliberately bypass key lookup.

The smallest proposed fix boundary is concrete reflective allocation used by normal object returns, fields and interface dispatch. Resolve only the demonstrated Class or selected Constructor, retain allocation identity, constructor invocation/access conditions and argument compatibility, and avoid classwide compatible-service enumeration. Constructor-array support follows that baseline. Before accepting broader coverage, retain missing-key, unknown-Class, null-target and incompatible-constructor negatives. Singleton reuse should retain the selected service object rather than invent a fresh classwide target.

This is a known-failure development probe, not an acceptance pass. The runner asserts that the direct baseline binds three capabilities and reports all other verdicts without hiding failures. Frozen oracle facts and production code are unchanged.
