# Real YSP registration and missing synthetic startup shape

The v11 constructor factory fixture passing does not prove News recovered: the unchanged YSP subset still misses 171 rows. The real service factory's class/constructor conditions are satisfied, but the selected class must first arrive through the actual initialized registry. This document supplements the previous source proof without changing gold. Exact source, fixture, jar and result hashes are in the companion JSON.

The manifest Application is TNApplication, whose constructor supplies a literal delegate class name to RFixProxyApplication. Its attachBaseContext reflects that class, creates the delegate, and calls a helper that finds and invokes `attach(Context)`. The delegate extends BaseApplication. The hidden Android attach-to-virtual-attachBaseContext edge has not been independently closed here; BaseApplication must not simply be relabeled as the manifest Application.

BaseApplication.attachBaseContext calls Services.init(false). The utility selects public static Loader.init with `Loader.class.getMethod("init", new Class[0])`, then passes that Method, null target and empty Object array through a reflection-monitor wrapper. The wrapper sets accessibility and calls Method.invoke. Loader.init calls the concrete module RouterEntry.init, which calls the generated service registration. The real registry has a static ConcurrentHashMap outer layer and a custom ConcurrentHashMap subclass inner layer; putWithCheck delegates to inherited virtual put. Services then uses several facade wrappers, Meta's default creator and synchronized singleton cache before returning the service.

The original probe instead registered the service directly from Activity.onCreate into an instance HashMap. It therefore omitted startup ordering, global registry side effects, ordinary reflected static method invocation, the proxy/delegate Application chain and custom concurrent-map writes. These are independent boundaries; the new probe isolates one rather than claiming all are fixed.

Run `test/run-service-startup-probe.sh`; optional jar/output arguments mirror the earlier runner. It compiles only the two test files against frozen v11. The fifteen cases place the registry in a static global field and initialize it through GeneratedLoader.init. With constructor-array service creation, explicit direct startup produces bridge, setting and callback facts. Changing only startup to Class.getMethod plus a wrapper Method.invoke loses all three categories. Selecting the same Method without invoking it is an explicit negative and also produces zero.

The constant-Class creator variants can produce facts even without a proven startup registration path, so they cannot certify registration execution. Some direct controls also produce duplicate receiver alternatives; this probe does not certify capability precision. Application-only cases define attachBaseContext but the direct Activity harness does not explicitly seed it, so their zeros alone are not proof about the complete APK lifecycle pipeline.

The next minimal generic repair boundary is executing the actually selected compatible public static method for ordinary side effects, including wrapper propagation and exact target/argument binding. An initialization method must not need a JavaScript annotation or transport registration to execute. Preserve the no-invocation negative and wrong-registry-key negative. Then independently verify real Application startup/global-state propagation and the custom Map subclass; no App service names or classwide target expansion are justified by this evidence.
