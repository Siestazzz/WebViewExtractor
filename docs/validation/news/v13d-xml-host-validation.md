# v13d XML host validation

This is a focused comparison of the four completed development hosts in v13d against v13c. Unknown alternatives remain unknown even when one member has the desired concrete type.

The tighter XML seed rule removes the clearest v13c false group: all eleven `AdWebView.initWebViewSettings` rows disappear from WebNovel, and that method has no call on the Novel source path. Privacy also loses uncalled data-loading overrides and incompatible helper alternatives. Support loses broad reset and override rows that XML class discovery alone did not justify.

Privacy’s direct binding is now strong. `setWebViewClient` and the eight common settings use the exact XML allocation ID and `X5WrapperWebView` type. The item Activity’s mixed-content call still includes a PatchRedirector alternative, so only its real XML member is proven. The pruning is slightly too strong: each Activity actually calls `loadUrl` on this field. Runtime virtual dispatch enters `X5WrapperWebView.loadUrl`, then `DtX5WebView.loadUrl`; the latter calls `injectBridge`, which conditionally installs two interfaces. Removing those loadUrl and bridge sites is a real recall loss, while removal of uncalled `loadData` variants is correct.

Novel’s genuine field chain improves without becoming unique. Every setting in `NovelWebView.setWebViewSettings`, including `setBlockNetworkImage`, now has the nested `AdWebView` allocation as an alternative with the correct inner XML evidence. Both client registrations also contain that same allocation. Thus their eleven callback implementations are source true for the AdWebView. The union still contains PatchRedirector-return and PatchRedirector-derived field alternatives typed `BaseSysWebView`; the whole receiver must remain candidate/unknown rather than being accepted solely because one alternative matches.

Support’s clients and BaseWebView constructor defaults use the precise XML object. Its three direct `initView` settings retain the same `activity/view:2131303125` ID but remain typed as `smtt.WebView`; concrete type propagation across the parent-declared field is still incomplete. The twelve-row DtX5 group under `utils.r.ˆ` remains false for the normal lifecycle. `m150665(WebView)` allocates `DtX5WebView` only when its argument is null, while Support calls it with the XML field after initialization. This fallback needs guard/order feasibility rather than ordinary allocation reachability.

Several removals in Novel also deserve caution. The Activity really loads the inner view through `WebViewBridge`, and BaseSysWebView can conditionally execute its file-access helper while loading. Removing every inherited load/helper site is therefore not automatically correct. The reusable boundary is actual invocation: XML discovery may seed constructors and genuine View lifecycle methods, while ordinary methods enter only through a real call, including virtual override dispatch.
