# v17 work in progress: reserve time to preserve executed startup state

Code inspection finds a coupled deadline in ApplicationBootstrap: traversal and extraction of the reachable static heap both use the same one-second stop. When traversal reaches that stop, the following heap loop exits before copying its first entry. This can discard writes that have already executed. A zero-entry startup snapshot is therefore not evidence that the App initializes no relevant state.

The change keeps the existing total budget and global deadline. It reserves ten percent of the remaining startup budget, capped at 100 ms, for the static closure. The execution deadline is earlier; snapshot extraction then uses the original total deadline. No extra method bodies are interpreted during copying. Existing context/reachability limits and partial-analysis diagnostics remain. Only actual static roots and their reachable objects are copied, using independent mutable containers when importing into each host.

ApplicationSnapshotBudgetFixture covers deterministic budget arithmetic, an expired execution deadline followed by a valid closure deadline, preservation of an already executed static object/child/map chain, exclusion of an unrelated instance, independent per-host maps, retained partial diagnostics and an expired total deadline. The complete capabilitySelfTest, compactReportTest and shadowJar suite passes in 23 seconds (test/runs/generic-v17-bootstrap-reserve-tests.log).

This is a v17 worktree change, not part of frozen v16. It has not yet been measured on the ten APKs. Reserving copying time reduces traversal time and can lose a late initialization that previously completed; real-App comparisons must check that tradeoff. It cannot recover writes never reached, prove proxy Application dispatch or fix all static-registration paths. In particular the observed Xigua startup static_heap=0 alone does not establish that this repair will recover its missing Browser surfaces.
