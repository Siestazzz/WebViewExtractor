# Generic v12: allocation-local Class carriers

The frozen v11 Mango run expanded global relevant methods from 26,862 (v10) to 46,819, while the capability API seed count remained 670. At the 325-second checkpoint, 115 roots were still pending; v10 finished with limits in about 140 seconds. A live thread dump showed workers evaluating nested method returns. This is evidence of a performance regression, not proof that this single change accounts for all its cost.

v11 added every type with an instance Class field to `bindingObjects`. That set also participates in global return/field relevance expansion. v12 separates `classValueCarriers`: the actual reached allocation and constructor still capture their Class arguments, but merely declaring a Class field no longer marks the holder's factories and callers as capability-relevant. Existing WebView/Client holders and structurally recognized registries keep their prior relevance rules. No private App identifier is used.

The complete service factory regression remains required: metadata Class field, nested registry, interface creator, reflection constructor, singleton cache, product and actual WebView attachment. After this separation, the full capabilitySelfTest and compactReportTest passed in 13 seconds (`test/runs/generic-v12-class-carrier-tests.log`). The focused ClassCarrierRelevanceFixture now reproduces the irrelevant factory expansion against frozen v11 and excludes it in v12 while preserving real capability roots and the twelve service paths. See GENERIC_V12_CLASS_CARRIER_RELEVANCE_TEST.md. In the first terminal v12 Mango run, total time is146.524s and the matched counts remain Bridge1215/1259, Settings565/608, callbacks587/662. This supports recovery of that development-run regression, not the final isolated performance gate.
