# Browser runtime diagnosis before the v16 batch completes

This review uses the frozen v15 report and existing source evidence; it does not inspect application decompilation or run another APK analysis. The accompanying JSON preserves the report hash, aggregate metrics, bootstrap diagnostics, and five exact host coverage records.

All five Browser hosts are unfinished in phase 1. Browser processed 3,475 contexts with 1,595 pending; Aggregation 3,268/1,644; Pure 3,261/1,615; Pad 3,133/1,604; PadDialog 2,708/1,477. Their pending priority lanes are empty. Browser's sampled queue includes 487 BaseSettings.addItem contexts reached through AppSettings construction, plugin file construction, and AndroidX Fragment state transitions. APK-wide there are 498,871 pending contexts and 6,645,923 retained heap entries. This proves unfinished traversal and substantial initialization costs, rather than proving where the actual Browser installation chain first becomes unknown.

Application startup processed two contexts, exhausted its local time budget, and exported zero static heap entries. The execution/closure deadline interaction can discard already executed startup writes. However, scene-installation-source-chain.json identifies the Browser root factory as returning the Activity's retained this.t object. That evidence does not establish that this particular root requires Application bootstrap state. Zero startup state remains a possible upstream dependency for other service calls, not a confirmed first break for these five hosts.

A concrete engine cost defect is visible without guessing application behavior: processJob consumes transaction add/replace/remove/commit through the exact protocol model, but modeled manager getters, beginTransaction, and fluent show still fall through to ordinary callee scheduling. Their return expressions have already been replaced by manager/transaction identities. When packaged SDK bodies are relevant, those calls can additionally enter the SDK state machine. The queue sample is consistent with this path, but its frequency alone does not prove every state-machine job originated from a modeled entry; restore/lifecycle paths also exist.

The proposed correction consumes only an exact supported protocol call after known compatible actual receivers and dispatch to a modeled SDK declaration have been established. Application overrides retain their real bodies; unsupported methods and unresolved receivers retain ordinary processing. A regression must retain installed Fragment capabilities, exclude noise reached solely through a modeled SDK body, execute an application override, and preserve uncommitted/null negatives. No broad AndroidX prefix exclusion is justified.

After the batch finishes, a single-host trace should record actual stages rather than infer them from missing facts: Activity retained root creation, factory return identity, lifecycle Fragment transaction commit, Scene dispatcher invocation, assigned-container identity, native wrapper installation, and later delegate assignment. Each stage must distinguish not visited, pending, unknown receiver, and visited concrete identity. Existing synthetic factory and wrapper successes do not prove the actual APK chain completes.
